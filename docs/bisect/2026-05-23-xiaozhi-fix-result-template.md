## 9) 下一步建议区

### 若判定为 GOOD

- 确认修复方向有效，将补丁 commit 记录为 BAD→GOOD 转换点
- 若 artifact-only 标记仍在：优先补齐构建 provenance（提取 app_desc、记录构建日志）
- 建议在更多候选点（如 `0f66193` 裸 revert）上做交叉验证，排除"恰好编译环境差异导致恢复"的可能性
- 考虑将该修复合并到主线，进入集成测试

### 若判定为 BAD

- 记录失败类型与轮次，用于下一步修复迭代
- 若为 `context_lost` 或 `state_stuck`：回到 `application.cc` 的 `HandleStateChangedEvent` / TTS 状态切换逻辑继续排查
- 若为 `asr_fail` 或 `no_response`：检查修复补丁是否意外破坏了音频链路初始化
- 建议先回到 `0f66193`（裸 revert 无补丁）验证基线行为，区分"修复无效"与"修复引入了新问题"

### 若判定为 FLAKE

- 不推进结论，标注待复测
- 建议增补复测次数（至少 5 次），并在复测中固定环境变量（网络时段、麦克风位置、说话语速/音量）
- 若复测后仍 FLAKE：记录为"该修复方向不稳定"，不纳入 bisect 边界

### 若判定为 STOP

- 记录触发 STOP 的具体条件与时间
- 仅允许进行环境修复（网络恢复、账号重登、设备重启后重建基线）
- 环境修复后用已知 GOOD 锚点重建基线后再试本候选点
- 不得在 STOP 后强行给出 GOOD/BAD 结论
