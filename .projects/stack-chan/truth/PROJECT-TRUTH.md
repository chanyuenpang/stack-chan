# StackChan Project Truth

## 项目级约定

- canonical truth 文档按知识主题归档，不按一次性任务归档；长期功能规则放入 `features/`，架构决策放入 `adr/`。
- firmware dev/实验控制能力默认不等同于生产 API；涉及设备控制、音频注入、MCP tool 时，必须先确认编译开关、真实入口、调用链路与安全边界。
- 与 XiaoZhi、MCP、音频队列、HTTP 控制面相关的调查要优先保留“真实调用链路”和“不要改错的位置”，避免只记录本次验证状态。
- “HTTP 调用 MCP tool”必须先区分本地 LAN dev HTTP `/dev/mcp/call` 与小智官方 HTTP Messaging API `/api/messaging/device/tools/list|call`：两者鉴权、请求字段、可见 tool 范围和调用链路不同。`self.system.reboot` 已在 MCP 注册层存在，也已显式接入本地 `/dev/mcp/call` 的 `stackchan_mcp_dispatch_tool()`；`remote_control.py` 支持完整 `self.*` tool name，并提供 `reboot --confirm` CLI。长期黄金入口是 `/dev/mcp/call` + `self.system.reboot` + `confirm=true`，不要误以为存在独立 `/dev/reboot`。
- 与 OpenClaw plan 完成后触发 StackChan 庆祝链路相关的调查，短期优先查 `after_tool_call` 过滤 `plan_edit` / `plan_write` 和落盘 plan 状态；不要把未接线的 `planEventListeners` 或 `subagent_ended` 当成 plan task done 信号。
- OTA 调试必须区分 app OTA、NVS 配置和擦机：`wifi.ota_url` 可覆盖官方 OTA URL，清空 `wifi/ota_url` 会回退到 `CONFIG_OTA_URL` 官方地址，也可只修补 NVS 分区写成本地 OTA URL；`firmware.force` 数字 `1` 可强制更新；本地 manifest 不应携带会覆盖激活、MQTT/WebSocket 或 assets 状态的字段。
- 真实设备 OTA 验收要拆成“OTA 前半段闭环”和“reboot 后目标版本确认”两个阶段：`Ota: Current version`、`New version available`、`Writing to partition ota_1`、`Progress: 100%`、`Firmware upgrade successful`、`Application: Firmware upgrade successful, rebooting...` 足以证明下载、写 OTA 分区、设置 boot partition 和 reboot 前 `boot/start_once` 写入；但 USB 重连可能漏掉最早启动日志，必须用 `Project name` / `App version` / `BOOT-MODE`、UI 版本或只读分区状态确认新 app。重启后只看到 Launcher `SERVO-MOVE`、无 Wi-Fi/HTTP/tcpdump 请求，只能写“未观察到”，不能反推 OTA 写入失败。
- StackChan 存在 MoonCake Launcher 与 XiaoZhi runtime 两阶段能力边界：`firmware/main/main.cpp::app_main()` 先安装 `LAUNCHER`、`SETUP`、`AVATAR`、`ESPNOW.REMOTE`、`APP.CENTER`、`EZDATA`、`DANCE`、`AI.AGENT` 等 apps；`AI.AGENT` 是边界 app，打开后才进入 `Hal::startXiaozhi()`。`SETUP -> About/System Update -> SystemUpdateWorker` 可在 Launcher 阶段手动触发 `GetHAL().updateFirmware()`，但 HTTP 18080、MCP tools、reminder/celebrate、dev local control 都属于 `startXiaozhi()` 后能力，dev serial 当前 no-op。详见 `features/mooncake-launcher-capability-map.md`。
- XiaoZhi 自动启动 / reboot loop 排查必须先区分 boot mode 逻辑、Launcher autonomous OTA 网络初始化和 XiaoZhi `Application::Initialize()` 网络初始化：`boot/start_once` 当前不受 `fail_count` 保护，OTA 成功后的 `set_boot_autostart_once_for_ota()` 会写 `default_mode=xiaozhi + start_once=true + fail_count=0`；若串口出现 `***ERROR*** A stack overflow in task sys_evt has been detected.`，P0 主线是 `CONFIG_ESP_SYSTEM_EVENT_TASK_STACK_SIZE=4096` 与 Wi-Fi event callback 栈，而不是 OTA URL 或 `AI.AGENT` 生命周期。详见 `features/boot-mode-xiaozhi-autostart-and-sys-evt-overflow.md`。
- StackChan OTA 检查还有 Launcher 前置门槛：设备停在 `mooncake Launcher` 图标网格时，传统 XiaoZhi `ActivationTask::CheckNewVersion()` / `ota_->CheckVersion()` 不会触发；server 无 `POST /ota/` 不一定是 OTA server 或 manifest 错。当前固件已有 NVS boot mode 驱动的 Launcher auto-open `AI.AGENT` 机制：`boot/start_once` / `boot/default_mode` 经 `get_boot_mode_xiaozhi_auto_open_source()` 与 `requestAutoOpenAiAgent()` 进入 MoonCake `openApp(AI.AGENT)` 生命周期；但 USB serial、HTTP 18080、MCP bridge 仍不能在纯 Launcher 阶段替代触摸或 boot mode。2.0.32 / 2.0.33 的 default_off / `launcher_only` 口径下，Launcher 不自动启动 Wi-Fi/OTA，脱困路径依赖触摸打开 `AI.AGENT` 或 `SETUP -> Firmware -> Check for Updates`；若 UI 完全不可用且不允许 USB/NVS 写入，则当前正式固件没有可靠非 UI 脱困入口。`start_once` 不受 `fail_count` 保护，`default_mode=xiaozhi` 才有 fail_count 阈值；NVS `warm_boot/app_index` 只滚动图标不触发点击。详见 `features/launcher-no-network-recovery-paths.md`、`features/launcher-to-xiaozhi-startup-chain.md` 与 `features/boot-mode-xiaozhi-autostart-and-sys-evt-overflow.md`。
- 配网 AP 能打开不等于 OTA URL 已写入；若 `POST /advanced/submit`、`POST /submit`、`POST /exit` 全部 `501 Not Implemented`，应先排查 `WifiConfigurationAp::StartWebServer()` 的 handler 注册/匹配或改用 USB/NVS 读取确认，不要声称 `ota_url` 已改好。
- 重打包、OTA 或崩溃回归排查必须先核对 `PROJECT_VER`、bin 内版本、manifest `firmware.version`、实际 bin 路径和 SHA256；不要把目录名、脚本默认值或包名当作真实版本。`ops/bin/stackchan-doctor` 是 OTA 工具链发布 / 排障前的只读自检入口：默认检查 user `stackchan-ota.service`、`GET/POST /ota/`、`HEAD /stack-chan.bin`、`active.json`、active bin size/sha256、app desc version、USB 串口和 token 存在性；默认不访问设备状态，`--check-device` 才只读 `GET /dev/status`；重启、写 NVS、触发 OTA、刷固件必须保持 `skipped_destructive`。
- 点击进入 XiaoZhi/App 崩溃类排查不能只盯 Dev HTTP；还必须核对 `_stackchan_update_task()` 在非 idle / App 初始化阶段是否保持 2.0.5 的保守更新窗口，特别是 50ms wake、active motion tick、重复 `motion.update()` 与 `LVGL lock` 竞争。
- `self.robot.celebrate` 执行后若出现 USB 枚举消失、网络离线、无 panic，不要只归因于外部供电；长期主线是庆祝在同一更新任务内叠加满亮 LED、两轴舵机 final-target 阶跃写入与 SCS UART ACK/读写等待。no-op 只算保命，恢复庆祝必须有功耗/力矩/总线预算、舵机总线隔离和 reset reason 证据链。启动阶段与 scheduler release/stop 阶段都必须 no-read：`moveWithSpeedNoHardwareRead()` 避免启动读，`Servo::stopAnimation()` / `abortAnimationNoRead()` 使用 `_angle_anim.directValue()`，日志以 `SERVO-DIAG ... read_hardware=0` 和 `SERVO-SCHED ... bus_healthy=0|1` 为验收锚点；正常 auto sync 仍可在 `allowHardwareSync && _auto_angle_sync_enabled` 时读硬件。
- 串口持续出现双轴 `SERVO-BUS recovery_probe_failed reason=update_tick raw=-1` 时，应判定伺服总线仍处于恢复失败循环；HTTP `/dev/status`、ping、USB 枚举或 heap 稳定只能说明主系统未硬死，不能证明庆祝动作或舵机总线健康。bus_dead 恢复应按 `stage=flush`、`stage=quiet`、`stage=ping`、`stage=read_pos`、`event=recovered` 分阶段推进，并且只有 `Ping` 成功后才 `ReadPos`。
- `ReadPos` 黑屏/卡死链路的项目级规则：任何 `ReadPos` / `WritePos` / `Ping` / `ReadMove` 等 SCS UART 同步事务都不应在 `LvglLockGuard` / `lvgl_port_lock` 内执行；异常 `ReadPos` 可阻塞约 `100-280ms`，会拖住 LVGL 渲染。双 update 路径、MCP/httpd 回调与 yaw/pitch 共享 `_scs_bus` 会放大问题；第一阶段串行化已落在 `SCS` 基类协议层（`SCS.cpp` / `SCS.h`），所有 UART 事务共用全局 FreeRTOS mutex，`50ms` 获取超时，owner task 递归安全，并用 `SERVO-IO` 记录异常/慢事务。后续修复仍要推进 UI 锁隔离、硬超时和 motion update 去重。
- `SCS::beginBusTransaction()` / `SCS::endBusTransaction()` 这类舵机 UART 公共诊断日志是关键错误路径，不只是辅助日志；在 `CONFIG_LIBC_NEWLIB_NANO_FORMAT=1` 下禁止使用 `%lld` / `%llu` 等 64 位 printf 格式。2.0.34 的 Guru Meditation boot loop 根因是 `SCS.cpp` 的 `duration_ms=%lld` 导致 nano-vfprintf 参数错位，后续 `%s` 解引用垃圾指针触发 `_printf_i` / `LoadProhibited`；健康 boot 不触发失败日志时该 bug 会潜伏。详见 `features/scs-nano-vfprintf-guru-meditation.md`。
